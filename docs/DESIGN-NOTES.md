# Design Notes

Design reasoning and measurements behind larger changes. The binding rules are summarised in the project `CLAUDE.md`; this file explains why they exist. One section per step.

## Single firmware for Waveshare 1.64" V1 and V2 (runtime board detection)

Before this change V1 and V2 boards needed separate firmware images, and the wrong image gave a black screen (so nothing could even tell the user what was wrong). One image now supports both and works out the board at boot.

### Findings that made one image possible

- Waveshare's V1 and V2 ("V1.1") demos use the same `esp_lcd_sh8601` driver, init table, X offset (20 px) and 40 MHz QSPI clock. The only proven display difference is the chip-select pin: GPIO9 on V1, GPIO46 on V2. Hardware spike confirmed: colour bars render correctly on CS9 (V1) and CS46 (V2) through the same driver, so the Arduino_GFX CO5300 path was dropped.
- Both boards have the same MCU, flash, PSRAM and I2C devices (FT3168 touch at 0x38, QMI8658 IMU at 0x6B), so none of those can identify the board.
- HX711 SCK and motor wiring (V1: GPIO2 / GPIO18, V2: GPIO1 / GPIO16) are a project wiring convention, not something the board dictates.

### Board detection

Implemented in `src/hardware/board_detect.cpp` (pin reads, NVS, panel probe) and `src/hardware/board_decide.cpp` (pure `decide_variant()`, unit-tested on the host in `test_native`).

Signals, in order:

1. **GPIO45 with internal pull-up** (primary). V2 holds GPIO45 low (the panel TE line, held low by the board, measured); V1 leaves it floating so it reads high. 0 means V2 candidate, 1 means V1. GPIO45 was chosen over GPIO18 because GPIO45 is not a user wire.
2. **V2 confirmation**: the panel is brought up on CS=GPIO46 and TE edges on GPIO45 are counted for 100 ms (`HW_BOARD_TE_WINDOW_MS`). A V2 panel produces about 60 Hz TE (~12 edges per window); V1 produces none. At least `BOARD_TE_MIN_EDGES` (6) edges are required.
3. **GPIO18 with internal pull-down** (hint; a conflicting level can veto to UNKNOWN/cached board). V2 holds it high (touch interrupt with 4.7k pull-up); a bare V1 reads low. It is never the primary signal because on V1 it is the user's motor wire and may legitimately be pulled high.

Contradictory or missing evidence gives the cached value (`board_last` in NVS) for display only, or UNKNOWN when there is no cache. A user override (`board_override` in NVS: 0 auto, 1 V1, 2 V2) skips probing completely. A successful PROBE result is written to `board_last`.

Why not the obvious approaches:

- A bit-banged CO5300/SH8601 ID read (command 03h, register DA/DB/DC, 16 timing variants, both CS pins) got no answer on either board. Dropped.
- Reading I2C addresses, chip ID, flash or PSRAM: identical on both boards.

Evidence base: one V1 and one V2 board. A second V2 board would raise confidence.

### Safety rules for the motor

GPIO18 is the motor output on a V1 wiring but a touch interrupt input (with pull-up) on V2. Driving it on a V2 fights the touch controller and can leak voltage into the grinder input. Hence:

- At the top of `setup()`, `board_park_pins()` drives GPIO16 low and puts GPIO18 into input with pull-down. GPIO18 is never an output before the board is known.
- The motor is enabled only when the board was established by **PROBE or USER**. UNKNOWN and CACHED boards get `motor_pin = -1`, `Grinder::init(-1)` leaves the grinder uninitialised and the UI shows a motor-disabled notice. An unknown board must never default to the V1 motor pin.
- `board_motor_pin_allowed()` is an allow-list check: it rejects UNKNOWN boards, GPIO18 on V2, and display, touch, IMU, HX711, strapping, USB, UART, flash and PSRAM pins.
- Forcing V1 on a real V2 (user override) would drive GPIO18 against the touch interrupt. This is why the BLE override of V1/V2 is only accepted while the board is not established (see picker/override below) and why the docs warn about it.

### Dual wiring (HX711 and motor)

Both known wirings are active at once so the user does not have to tell the firmware which one they built:

- HX711 clock is pulsed on GPIO1 and GPIO2 together (`loadcell_sck_pin` plus `loadcell_sck_pin_alt`, mask in `hx711_clock_mask.h`); DOUT is GPIO3 on both. The unused pin is simply an unconnected output.
- Motor: GPIO16 always (when the board is established), plus GPIO18 only when the variant is V1 and was established by PROBE or USER. Never on V2 or UNKNOWN.

### Display design

One backend: Waveshare's `esp_lcd` SH8601 driver (`src/hardware/esp_lcd_sh8601.c`) driven by `DisplayManager`. Board-specific values (CS pin, X offset, QSPI clock) come from `board()`.

Render path, as built:

- LVGL renders partially into a **40-row buffer in PSRAM** (`HW_DISPLAY_DRAW_BUF_ROWS_PSRAM`, 22.4 KB, about 12 strips per full redraw).
- Each strip is copied in chunks through **two internal DMA staging buffers** (`HW_DISPLAY_STAGING_ROWS` = 8 rows each, 4.5 KB each) and sent while the next chunk is copied. A semaphore signalled from the `on_color_trans_done` callback paces the transfers.
- Fallback when the PSRAM or staging allocation fails: a small internal DMA draw buffer (8 rows, 57 strips per redraw) sent directly. Staging rows halve down to `HW_DISPLAY_STAGING_MIN_ROWS` (4) on allocation failure.

Why PSRAM-direct failed: the first attempt handed the PSRAM LVGL buffer straight to `esp_lcd_panel_draw_bitmap()`. On hardware this logged `spi transmit (queue) color failed`, because esp_lcd queues the colour data for DMA and a queued transfer from PSRAM does not work with this SPI configuration, so the display stopped updating. Hence the extra copy through internal DMA staging buffers. (Hardware note: the SPI bus `max_transfer_sz` is sized for one chunk of the larger of staging and internal draw rows, 8 rows = 4480 B, not a full frame, to save internal RAM.)

Measurements on V1 (UIRender task, per 10 s): released rc.2 (Arduino_GFX) about 477 cycles, 20 ms average; build #44 with this design about 302-306 cycles, 32-33 ms average; build #70 about 310 cycles, 32 ms. Staging with 4 rows was slower (166-213 cycles, 46 ms), so 8 rows is used. The user judged the feel much better than rc.2 regardless. Possible follow-up: second PSRAM render buffer to overlap rendering and transfer.

Re-init safety: `release_panel()` must run before `init_panel()` again (used by the board probe and degraded mode).

### UI/BLE reporting and override

- Menu → **Hardware board** page: shows `V1/V2 (source)` and an Auto / V1 / V2 radio group. The choice is stored in NVS (`board_override`) and applies after a restart.
- BLE debug command `0x03` + `0|1|2` (`BLE_DEBUG_CMD_SET_BOARD`, wrapped by `python3 tools/grinder.py board v1|v2|auto`). `auto` is always accepted (it cannot enable the motor). `v1`/`v2` are accepted only while the board is **not** established by PROBE or USER, as a recovery path; once established the override can only be changed on the device.
- The system-info JSON reports `board` and `board_src`. Diagnostics codes `BOARD_UNRECOGNIZED` and `MOTOR_DISABLED` raise the warning icon.

### On-screen board picker (degraded display)

When the board is UNKNOWN the panel is driven on **both** chip selects (CS9 and CS46): every strip is sent twice, and only the panel that is really wired answers. This works because the staged flush path sends from one buffer. On top of that the UI shows a V1 / V2 picker. The choice is stored as a USER override and the device restarts after `HW_BOARD_PICKER_RESTART_DELAY_MS` (1.5 s); if saving fails the picker reappears after 2 s. Mirroring needs the staging buffers; without them the mirror panel is disabled.

A wrong pick on the real board is recoverable through BLE (`board auto`) or the Hardware board menu page.

A V1 user with GPIO18 pulled high by external wiring reads as a conflict (GPIO45 high, GPIO18 high), ends up UNKNOWN and gets the picker; this is intentional rather than guessing.

### Single image, build and release

- One PlatformIO env builds the production image (`waveshare-esp32s3-touch-amoled-164`); debug and mock envs derive from it. The `-v2` env and `HW_DISPLAY_VARIANT_V2` style compile-time macros are gone.
- `release.yml` builds and publishes one image under the base artifact names. `deploy-web-flasher.yml` keeps the separate V1/V2 entries for old tags and labels new releases "V1 + V2 (auto-detect)".
- `tools/grinder.py --variant` is accepted but deprecated and ignored (prints a warning). Delta OTA bases are looked up in `firmware_cache/<env>/build_NNN.bin`; for the main env the legacy flat cache and the old `-v2` cache dir are also searched, and if the candidates differ the base is ambiguous and a full update is sent.
- Merged flash images must use `--flash-mode dio` (bootloader is DIO for the octal-PSRAM build).
- Bare `grinder.py upload` uploads `.pio/build/waveshare-esp32s3-touch-amoled-164/firmware.bin`, so it needs a build of the main env; a debug or mock build is not picked up automatically (pass the path explicitly).

### LVGL allocator and heap

LVGL allocates from PSRAM (`src/ui/lvgl_psram_alloc.cpp`, falling back to internal RAM) so internal RAM is left for BLE and task stacks. Internal heap is still the scarce resource, but the old "6-7 KB free" figure (pre-PSRAM LVGL, builds #44-#70) is obsolete. Measured on a V2 board, build #141, free internal heap: **258 KB after hardware init -> 252 KB after UI init -> 173 KB after BLE enable (BLE stack costs about 79 KB) -> about 134 KB steady**. WiFi costs more on top (measured in the WiFi spike, conditions differ from the numbers above): `WiFi.mode(STA)` about 42 KB, and with WiFi, the HTTP server, mDNS and BLE advertising all running the lowest free internal heap in gate G1 was 52.8 KB. On COM15 the free heap at the start of a pull job was 47.7-56.5 KB, with TLS dipping about 9 KB below that (see the HTTPS pull engine section). The 134 KB steady figure was taken without WiFi. Boot logs `[HEAP]` lines before UI init, after UI init and after BLE enable, plus `[STARTUP] Free internal heap after hardware init`. Re-measure before adding features that need internal RAM, including the UNKNOWN (mirror) path, which holds an extra panel handle.

### BLE soft disable

- **Why:** repeated `BLEDevice::deinit()`/`init()` leaked ~11 KB of internal heap per cycle and crashed the V2 board after 8-12 cycles (stack canary panic in the 1 KB `ipc0` task, which the BT controller uses for interrupt allocation; heap exhaustion at the same cadence). Moving the caller to another core does not help because the work always runs on ipc0.
- **What:** `BluetoothManager::disable()` no longer deinitialises BLE. It aborts OTA/data export, stops advertising, disconnects the client and marks BLE disabled; the stack stays resident (~79 KB internal RAM) and `handle()` keeps advertising stopped. The first `enable()` after boot does the full init; later calls only restart advertising on the existing server and services (characteristic pointers stay valid). Connections and writes arriving while disabled are refused.
- **Flags and envs:** `DEBUG_BLE_HARD_DEINIT=1` restores the old teardown for comparison. `DEBUG_BLE_ENABLE_STRESS=1` runs 150 disable/enable cycles from a Core 1 task and 150 from a Core 0 task (`[BLESTRESS]` log lines, panic-surviving state in RTC memory). Envs: `waveshare-esp32s3-touch-amoled-164-ble-stress` (soft) and `...-ble-stress-harddeinit` (baseline).
- **Measured (V2):** 300 cycles, 0 crashes, free internal heap flat at 126.5-128.9 KB.
- **WiFi spike:** its "BLE off" phases only free RAM when built with `-DDEBUG_BLE_HARD_DEINIT=1`.
- **Residual:** the first init at boot still goes through ipc0 (has worked in practice); the soft re-enable path is not yet tested with a real client.

### WiFi manager (chg008 pass 1)

- `src/network/wifi_manager.*` connects as a station from NVS namespace `wifi` (`ssid`, `pass`, `token`, `push_enabled`, `name`). `begin()` runs last in `setup()` and only reads NVS; all radio work (WiFi, mDNS) runs in `tick()` on the Bluetooth task (stack raised to 8 KB), with backoff 5 s doubling to 60 s (at least 30 s after an authentication failure). No credentials means the radio is never started.
- SSID, password and API token are stored in **plaintext** NVS (no flash/NVS encryption). Logs never contain them; the `[WIFI]` serial lines show state, IP, RSSI and disconnect reason only.
- BLE provisioning (debug RX): `[0x04][ssid_len][ssid][pass_len][pass][token16]` and `[0x05]`. The PC generates the 16-char lowercase hex token. Accepted only while no credentials are stored or `WiFiManager::provisioning_window_open()` (the WiFi menu page, see below); so changing credentials later is only possible through that menu window. Pure parsing/validation lives in `wifi_credentials.*` (host tests).
- Dev builds: env `...-wifi-dev` (`DEBUG_WIFI_DEV_CREDS=1`) seeds credentials from the gitignored `include/spike_secrets.h` when NVS is empty and arms `push_enabled`; the API token comes from optional `SPIKE_API_TOKEN`, else the fixed public dev token in `wifi_manager.cpp` (a loud `[WIFI] WARNING` boot line appears while that fallback is stored). **Erase NVS after using the wifi-dev env** (`pio run -t erase`, or the BLE clear command `0x05` from a normal build): it seeds a public dev token and `push_enabled=true` that survive reflashing with a normal image.

### WiFi push update (chg008 pass 2-3)

- **Pieces:** `system/image_header` (header check), `system/update_sink_image` (ImageSink: `esp_ota_*` with sequential writes, SHA-256), `system/update_guard` (copy of the BLE OTA safety rules: busy check, lock_out, re-check, watchdog, task suspend, touch; release resumes tasks first), `network/update_http_logic` (pure: bearer parse, lockout, begin-JSON parser, session id) and `network/update_server` (esp_http_server on port 80). The BLE `OTAHandler` is untouched except for two checks: it refuses while `UpdateGuard::is_held()`, and the guard asks `is_updating_synchronized()` (takes the OTA op mutex) after claiming its slot, which closes the start race.
- **Serialisation:** one mutex in `UpdateServer` around every sink/guard call; handlers lock per chunk, never across a socket read; the tick only try-locks (inactivity abort after `UPDATE_INACTIVITY_TIMEOUT_MS`).
- **Gate:** the server runs only while WiFi is connected and `push_enabled` is set (checked every 2 s from the Bluetooth task); mDNS `_http._tcp` follows it. The Accept prompt hook is `UpdateAcceptPolicy` (see the R2a/R2b sections: a tap on the grinder is required unless Confirm is switched off).
- **Endpoints:** `GET /api/info`; `POST /api/update/begin` (Bearer; `{"size","sha256"[,"build","version"]}` -> `{"session"}`); `PUT /api/update/data` (Bearer + `X-Session`, Content-Length == size) -> `{"status":"installed"}`, restart 800 ms later. Three bad tokens lock authentication for 60 s (doubling to 15 min, reset on success). Errors are `{"error","reason"}`; 409 busy, 413 size, 422 invalid image/SHA, 429 locked.
- **Tool:** `tools/wifi/grinder-wifi.py` (stdlib only), also `grinder.py wifi-info` / `wifi-upload`. Host and token from arguments, `GRINDER_WIFI_HOST`/`GRINDER_WIFI_TOKEN` or `~/.grinder-wifi.json`.
- **Former gap, fixed in R2a:** a push now stores `new_build_nr` / `new_fw_ver` like the BLE path (see the Accept prompt section).

- **No NVS while updating:** `tick()` skips all NVS reads (the push_enabled gate) while a session, the installed state or the guard is active. The data PUT authenticates against a RAM copy of the token taken at `begin` (zeroized when the session ends); only `begin` reads NVS, before the update takes the flash.
- **Early error replies:** every error reply except 401/429 is followed by a lingering close (discard up to 64 KB / 3 s of the request body, 1 s socket timeout) so the client receives the status instead of a TCP reset. The tool prints a hint when it still sees a reset.
- **Lockout:** a lock counts as expired when the unsigned distance to its end is 0 or larger than the longest lock (no re-arming after a millis() wrap).
- **Single httpd task limitations (accepted for now):** (1) one client trickling a header or body holds the only HTTP task until the 10 s receive timeout, so a LAN client can starve other requests; (2) the authentication lockout is global, so anyone on the LAN can lock the real user out with bad tokens (60 s, doubling to 15 min); (3) `/api/info` is not answered while a PUT is being received, so the tool must not poll it during an upload.
- **Measured throughput:** at -94 dBm (weak bench signal, `WIFI_PS_MIN_MODEM`) a push runs at 10-14 KB/s, about 4 minutes for the 2.2 MB image. Acceptable for a bootstrap; the 10 s receive timeout is the margin to watch on worse links.
- **Lingering close is a DoS lever:** any LAN client can keep the single HTTP task busy for about 3-4 s per lingering error reply (64 KB cap; the clock is checked between 1 s receives); 401 and 429 replies do not linger, but the pre-auth 403 (PUT without session) and 409 (busy) replies do, since they must reach the client. A PUT without a session is answered 403 before any token check (no lockout count), and a second `begin` while an update runs is answered 409 before authenticating (no NVS read).
- **Token staleness:** the RAM token copy is taken at `begin` and wiped when the session ends (success, error or timeout). If the token is re-provisioned mid-session, the running session keeps using the old one until it ends; the next `begin` reads NVS again.
- **Open items:** the Accept prompt, progress screen and the Receive/Confirm toggles exist (R2a/R2b, later sections); credentials/token provisioning tools exist since R3 (`grinder.py wifi-set` / `wifi-clear`, web flasher "WiFi Setup" tab, see the R3 section) but are host-tested only.

### WiFi menu page (chg008 R1)

- **Where:** Menu -> Settings -> "WiFi" (between Bluetooth and Display). Code is split out of the big files: `ui/screens/menu_screen_wifi.cpp` (page, window, refresh) and `ui/controllers/menu_controller_wifi.cpp` (Forget handler, 1 Hz refresh). Event `WIFI_FORGET`. No arm/Receive toggle yet (that comes with the Accept prompt, so token-only push is never reachable from the UI).
- **Content:** Status (Connected / Connecting... / Retry in Ns / Not set up, coloured), Network (shortened SSID), IP, Signal (`-62 dBm Good`), Name (`<host>.local`). "Not set up" block (shown without credentials) explains how to provision and warns when Bluetooth is off; "manage" block (with credentials) holds **Forget WiFi**, which opens a confirm dialog and then calls `WiFiManager::clear_credentials()` (SSID, password, token and push flag).
- **Pure text helpers:** `network/wifi_status_text.*` (host-tested): state text, RSSI quality (Excellent >= -55, Good >= -67, Fair >= -75, else Weak), SSID shortening (printable ASCII only, a run of other bytes becomes one `?`, max 20 chars with `...`). `WiFiState` moved there from `wifi_manager.h` so the helpers have no Arduino dependency.
- **Provisioning window:** `MenuScreen::sync_wifi_provisioning_window()` makes the window equal "menu visible AND WiFi page is the current page". It is called from the menu's page-change callback, from `show()` and from `hide()`, so every way of leaving the page or the MENU state closes it, and a menu shown again on the WiFi page reopens it. Serial log: `[UI] WiFi page entered/left (provisioning window open/closed)`.
- **Window security note:** the window stays open for as long as the WiFi page is on screen, including while the screen is dimmed (the page does not time out). During that time any BLE client in range can replace or clear the credentials through the unauthenticated debug write path (BLE link unencrypted). Accepted for now; leave the page when done.
- **Stale cache:** `WiFiManager::credentials_revision()` is incremented by `set_credentials()` and `clear_credentials()`; the 1 Hz refresh reloads the SSID/flag when it differs from the revision loaded last, so BLE provisioning or clearing while the page is open updates it. `clear_credentials()` returns false (nothing changed) if NVS cannot be opened; Forget then does not claim success.
- **NVS access:** the stored SSID and credentials flag are read on page entry (and after Forget, because the dialog hides the menu and `show()` re-syncs). The 1 Hz refresh only reads `WiFiManager` getters (state, IP, RSSI, retry time); labels are only touched when their text changed.
- **Not covered by tests:** the LVGL layout (280 px; Network, Signal and Name are stacked rows) needs a visual check on the device; "BLE write accepted only with the page open" needs a BLE client.

### WiFi Accept prompt, core part (chg008 R2a)

R2a is everything except LVGL. Without a UI controller (before R2b) **production builds fail closed**: the prompt cannot be answered, so every `begin` is refused with 409 `busy` ("Go to the home screen of the grinder"). Push stays disarmed by default.

- **Rendezvous:** `network/update_approval.*` is a pure state machine (IDLE / PENDING / ACCEPTED / DECLINED / EXPIRED / CANCELLED / UI_BUSY, injected time, wrap-safe, host-tested). `UpdateApprovalGate` (`update_approval_gate.*`, global `update_approval`) wraps it in a spinlock; the HTTP task files the request and polls every `UPDATE_PROMPT_POLL_MS` (50 ms) until it is no longer PENDING (the 30 s timeout expires it, so the wait always ends); the UI task will poll `pending_prompt()` and answer with `resolve()` / `resolve_busy()`. No LVGL call ever happens on the HTTP task. A late answer cannot overwrite an expiry or a cancel. Only a decline starts the 30 s back-off (`UPDATE_DECLINE_BACKOFF_MS`); expiry and busy do not.
- **Fail closed:** `UpdateApprovalGate::attach_ui(true)` is what the R2b controller will call. While no UI is attached the production policy answers `UI_BUSY` immediately (no wait, never accept).
- **Policy:** `UpdateAcceptPolicy::decide(request, peer_ip)` returns an `AcceptDecision`; the production implementation is `network/update_accept_policy.cpp`. Order in `handle_begin`: busy-before-auth check (guard held or an approval in use) -> bearer auth -> body parse -> grinder busy 409 (before bothering the user; the guard re-checks later) -> policy. Policy order: BLE client connected or data export running -> 409 "Disconnect Bluetooth first" (also with Confirm off) -> Confirm off (NVS `accept`=false) -> accept without prompt -> no UI -> UI_BUSY -> request (BACKOFF -> 429) -> wait. Replies come from the pure `accept_decision_reply()` (403 declined, 408 no_response, 409 busy, 429 declined_recently with `Retry-After` and `retry_after_s`).
- **Confirm setting:** `WiFiManager::accept_required()` / `set_accept_required()` (NVS `wifi/accept`, default true). It is served from a RAM copy loaded in `begin()` so `/api/info` ("confirm") and the policy never touch NVS while an update owns the flash. Turning it off only takes effect if the write succeeded; turning it on applies at once. `clear_credentials()` removes the key (back to the safe default). The start-up warning is logged only when Confirm is off.
- **Server tick:** a pending or just-answered approval counts as "in use": when the gate (WiFi up and push armed) disappears the tick withdraws the prompt (`cancel()`) and stops the server on a later round, never under a waiting handler (`httpd_stop` would wait for it). A second `begin` while an approval is in use is answered 409 before authentication. The single HTTP task is blocked for the whole wait, so `/api/info` and a second `begin` are only served after the first one was answered (documented limitation).
- **Prompt text:** `network/update_prompt_text.*` (host-tested): `prompt_sanitize` (printable ASCII only, every other byte `?`, max 32 characters), `prompt_format_size` (decimal units, `812 KB`, `2 MB`, `2.2 MB`) and `prompt_build_message` (4 lines, parts the client did not send are omitted, always fits `UPDATE_PROMPT_MESSAGE_BUF`). The peer address comes from `getpeername` on the request socket (IPv4 only, empty otherwise).
- **Progress:** `network/update_status.*` (`UpdateStatus` namespace, atomics plus a short reason string): AWAITING_APPROVAL / RECEIVING / VERIFYING / INSTALLED / FAILED, written by `UpdateServer` on every path (chunks, verify, install, sink/guard failures, the inactivity abort); `active()` is for the R2b `OtaDataExportController` guard. A FAILED status stays until the UI calls `acknowledge()` or the next update starts.
- **Expected-version marker:** `system/ota_marker.*` writes `new_build_nr` / `new_fw_ver` (namespace `grinder`, the BLE keys) with its own short-lived `Preferences` handle only after `guard_.acquire()` succeeded (so a concurrent BLE OTA's marker is never overwritten; the BLE path also writes after suspending the tasks) and before `sink_.begin()`; it is removed after `guard_.release()` on every later failure path (sink refusal, stream errors, verify failure, inactivity abort). Guard refusals never touch it. The BLE-connected check is repeated after the user accepted (a client may have connected meanwhile). After success the keys stay, so `check_ota_failure_after_boot()` reports a rolled-back or wrong-build update.
- **BLE exclusion:** `BluetoothManager::onConnect` disconnects a new client and `start_data_export()` refuses while `UpdateGuard::is_held()`; a connected BLE client makes `begin` answer 409 (the push does not disable BLE).
- **Dev knob:** `DEBUG_UPDATE_PROMPT_AUTOREPLY` (1 accept, 2 decline, 3 no reply; default 0) lets the HTTP side play the user; it is set to 1 only in the `...-wifi-dev` env and `#error`s without `DEBUG_WIFI_DEV_CREDS`. Other values are chosen with `-DDEBUG_UPDATE_PROMPT_AUTOREPLY=n` on top of that env.
- **Info disclosure:** `/api/info` is unauthenticated and now also reports `"confirm"` (whether Confirm is on), which tells a LAN client whether a tap is needed. Accepted; name, version, build and board were already public.
- **Tool:** `grinder-wifi.py upload` waits up to `PROMPT_WAIT_S` (45 s) for `begin`, prints "Confirm the update on the grinder screen (30 s)..." when `/api/info` says `confirm`, and explains 403/408/409/429 in plain words. The default firmware search now only considers the main env, `-debug` and `-wifi-dev` (not mock, selftest, spike, stress or deadman builds).
- **Not covered by tests:** the cross-thread wait on real hardware beyond the AUTOREPLY runs, the BLE-connected refusals (no BLE client from the dev PC), grind-in-progress refusal (no sensor), and everything LVGL (R2b).

### WiFi Accept prompt, UI part (chg008 R2b)

R2b is the LVGL side of R2a; with it the production build is no longer fail-closed (the controller calls `update_approval.attach_ui(true)` on its first frame) and push can be armed from the menu.

- **Controller:** `ui/controllers/wifi_update_controller.*` (`WifiUpdateUIController`, polled from `UIManager::update()` before `OtaDataExportController`; it returns true, which skips the rest of the frame, while the progress screen is up). No LVGL call happens on the HTTP task: the controller polls `update_approval.pending_prompt(&prompt, &generation)` (the generation is read under the same lock, so a replaced request is told apart from the one the dialog shows).
- **Accept dialog:** the existing confirm screen ("WIFI UPDATE", INSTALL in the accent colour, DECLINE), text from `prompt_build_message`. Allowed only while the UI state is READY or MENU, no blocking overlay is up and no update is active; otherwise `resolve_busy()` (HTTP 409 "Go to the home screen"). When the request expires or is cancelled while the dialog is up, `ConfirmUIController::dismiss()` closes it without running either callback; if some other screen took over the dialog (state no longer CONFIRM) the request is withdrawn. The decision table is the pure `update_prompt_action()` in `network/update_ui_logic.*` (host-tested).
- **Wake:** `ScreenTimeoutController::hold_awake(bool)` makes `update()` restore normal brightness and skip dimming. The controller holds while a request is pending, while the dialog is up and while the progress screen is shown, and releases it as soon as none of the three applies (so every resolution releases it). After the release, dimming resumes from the last touch time, so a prompt that expires on an unattended grinder dims again at once.
- **Progress screen:** the existing `ota_screen` (`show_ota_mode()`, title "WiFi update", arc = received/total), statuses "Receiving update...", "Verifying...", "Installed. Restarting...", "Failed: <reason>" (reason cut to `UPDATE_UI_REASON_MAX` = 16 characters, printable ASCII; plain "Update failed" without a reason). ### WiFi provisioning tools (chg008 R3)

**Status: host-tested only. Nothing in this section has run against a real BLE link** (the dev PC has no working BLE adapter). Every BLE step below is "NOT RUN on hardware".

- **Firmware unchanged.** Only `test_native/test_wifi_credentials.cpp` gained `test_parse_python_builder_frames`: five literal frames produced by the Python builder (basic, open network, UTF-8 SSID and password, 32 B SSID + 63 B password = 114 B, spaces/punctuation) that `wifi_parse_provisioning` must accept with the expected fields.
- **One protocol, three implementations:** `tools/wifi_provision.py` (Python: frame builder, validation, reply classifier, hardware-info parser, config writer) and `tools/web-flasher/wifi-setup.js` (JS twin) must stay byte-identical. The shared list is `tools/tests/wifi_provision_vectors.json` (checked by `tools/tests/test_wifi_provision.py` and `node --test tools/tests/wifi-setup.test.js`, also each side's reply-text table); the C++ literals above are copied from it, so changing the protocol means regenerating the JSON and the C++ literals together. Lengths are UTF-8 byte counts, password empty or 8-63, NUL rejected, token `[0-9a-f]{16}`.
- **`grinder.py wifi-set <ssid>` / `wifi-clear`** run `tools/ble/grinder-ble.py` (bleak). `wifi-set` validates SSID and password BEFORE scanning, prompts for the password with `getpass` (or `--password-env NAME`, or `--open`), generates the token with `secrets.token_hex(8)`, enables the debug stream (0x01), writes the frame with response, waits up to 5 s for the reply line, disables the stream (0x02). Only on a "stored" reply it writes the token (and the host `grindbyweight.local` only if the file has none, so a custom host is kept) through `grinder-wifi.py`'s 0600 writer into `~/.grinder-wifi.json` (other keys kept), so `wifi-upload` works with no manual config. Then it polls the BLE hardware-info characteristic (`wifi`, `ip`) for up to 40 s and reports the IP or a "not connected yet" warning. On "locked" (credentials exist, WiFi page closed) it says "open Menu -> WiFi"; on no reply it does NOT touch the config file. The token is printed masked, the password never.
- **Web flasher "WiFi Setup" tab** (`index.html` + `wifi-setup.js`): same flow with Web Bluetooth (`requestDevice` filter name `GrindByWeight`, optional services OTA/debug/sysinfo), token from `crypto.getRandomValues`, Copy and "Download config" (JSON identical to what the Python writer produces), "New token" button, "Remove WiFi from grinder". The module has no console output, no browser storage and no network access (asserted by the node test). It verifies through BLE (hardware info) because the HTTPS page cannot call the plain-HTTP device.
- **Hardware-info read, not notify:** the hardware characteristic is only refreshed every 10 s while a client is connected and its notification is cut at the ATT MTU, so both tools poll `read` (long read) every 3 s and ignore values that do not parse (stale or empty before the first refresh).
- **Known weak spots for the first hardware run:**
  1. The reply text arrives as debug-stream notifications. At the default ATT MTU of 23 a notification carries 20 bytes, so a message like `BLE_DEBUG: WiFi command rejected, credentials already stored...` would be cut and neither tool could classify it ("No reply" is shown, nothing is saved). Bleak on Windows/Linux and Chrome on Android normally negotiate a bigger MTU (firmware requests 517); if a client does not, the replies need to be shortened or sent in chunks (firmware change, not done here).
  2. The 114-byte set frame is a GATT long write when the MTU is 23 (new path; the older commands are 2 bytes).
  3. `grinder.py` pipes the child's output, so the password prompt relies on `getpass` talking to the terminal directly (POSIX `/dev/tty`, Windows console); stdout of the tool is buffered until exit like the other BLE commands.
  4. Chrome Android only exposes Web Bluetooth over HTTPS or localhost.
- **Security:** the BLE link is unencrypted, so a sniffer in radio range sees SSID, password and token while no credentials exist or the WiFi page is open (documented in the tab text and README). The token is generated on the PC/browser and never read back from the device.
- **Manual checklist (phone or second adapter):** first-time set; set while credentials exist and the page is closed (must be refused with the "open Menu -> WiFi" message and the config file unchanged); set with Menu -> WiFi open; clear; wrong password (status stays Connecting/Retry on the grinder, tool says "not connected yet"); open network; 32-byte SSID with a non-ASCII character; `wifi-upload` with the stored token afterwards; Chrome Android and desktop Chrome for the web tab.

### Boot-health rollback (chg008 R4)

- **Rule:** an image installed by an update (WiFi or BLE, both end in `esp_ota_set_boot_partition`) is PENDING_VERIFY on its first boot. `system/boot_health.*` overrides the Arduino core's weak `verifyRollbackLater()` (C linkage, returns true) so `initArduino()` no longer confirms it at once. `boot_health_tick()` (called from `loop()`) calls `esp_ota_mark_app_valid_cancel_rollback()` when `setup()` has finished and `millis() >= BOOT_HEALTH_CONFIRM_MS` (30 s). A reset or crash before that makes the bootloader mark the image ABORTED and boot the previous one (factory slot if there is no other valid app). Criterion deliberately tiny: no WiFi/BLE/sensor health, so a healthy image cannot fail to confirm. Pure decisions in `boot_health_logic.*` (host tests `test_boot_health.cpp`).
- **Images without a pending state** (USB-flashed, erased otadata, factory slot, already confirmed, state unreadable) are a silent no-op: `[BOOT] image state: UNDEFINED/VALID/...` is logged and nothing else happens. Logs: `[BOOT] image state: PENDING_VERIFY (partition ota_1)`, later `[BOOT] image confirmed after N ms`.
- **Updates are refused while pending.** `esp_ota_begin()` fails with `ESP_ERR_OTA_ROLLBACK_INVALID_STATE` on an unconfirmed image, so WiFi `begin` answers 409 "Firmware is still being verified, try again in a minute" and the BLE `start_ota` refuses with the same reason. Consequence: a second update needs the device to have run 30 s.
- **Marker lifetime:** `check_ota_failure_after_boot()` used to delete `new_build_nr` / `new_fw_ver` on a passed check at the first boot; the new image would thus consume the marker before crashing and the rolled-back image would never report the failure. Now a passed check keeps the marker while `boot_health_pending()`; `boot_health_tick()` clears it (`ota_marker_clear()`) right after the confirmation. After a rollback the previous image finds expected != current and shows the existing OTA_UPDATE_FAILED screen. A failed check still removes it at once. Caveat (pre-existing): if a version string is stored it is compared INSTEAD of the build, and many builds share a version, so the WiFi tool sends the build number only.
- **Fatal start-up failure:** if `task_manager.init()` fails, `boot_health_rollback_now()` calls `esp_ota_mark_app_invalid_rollback_and_reboot()` (no-op unless pending; returns if there is nothing to roll back to, then the old halt loop runs).
- **Expected behaviour:** a power cycle within 30 s of an update rolls back (the user sees "update failed"). The FIRST update from a firmware without R4 is not protected (the old firmware confirms the new image at once); protection starts with the next update. A hang in `setup()` (no reset) stays unconfirmed until the next reset/power cycle, which then rolls back.
- **WiFi tool fix:** `grinder-wifi.py upload` sent no build number when the image was not found in `firmware_cache/<main env>`, so no marker was stored for wifi-dev or test images. `find_cache_build` now searches every env directory of `firmware_cache` (main env first), and a timeout hint says "previous build is back, probably rolled back". Build only is sent, never a version. The server side (`http_parse_begin_request`, `ota_marker_store`) already accepted build-only (new host test with the tool's exact body).
- **Test env:** `...-boot-fail-test` (`DEBUG_BOOT_FAIL_TEST=1`, `-DDEBUG_BOOT_FAIL_TEST=2` for `esp_restart()`) crashes `DEBUG_BOOT_FAIL_DELAY_MS` (8 s) after boot, ONLY while the image is pending, so a USB-flashed copy never crash-loops. Not built by release.yml.
- **Confirmation failure:** if `esp_ota_mark_app_valid_cancel_rollback()` fails, `boot_health_tick()` logs it, keeps the image pending and the marker in place (a reset still rolls back and reports) and retries every 5 s.
- **Tool note:** after "Device is back" the WiFi tool reminds that the image is only confirmed after ~30 s of stable running (a crash before that rolls back); without a known build number it says a rollback cannot be detected.
- **Not covered:** the BLE path end to end (no BLE from the dev PC; reasoned from the shared bootloader mechanism), the bootloader's rollback itself (needs COM15).

### Release index and SemVer (chg008 R5)

**Status:** generator and parser only. The firmware does not fetch anything yet (pull engine is a later pass); real Pages output exists only after the next deploy.

- **Files:** the deploy-web-flasher workflow runs `tools/update_index.py` after the `firmware/index.json` step and writes `update-stable.json` and `update-beta.json` next to `index.html` (Pages root). No existing Pages file is touched. Trigger is unchanged (release published/unpublished/deleted, push to `tools/web-flasher/**`, manual).
- **Which releases:** only non-draft releases whose `smart-grind-by-weight-<tag>.manifest.json` name contains `auto-detect` (the unified V1+V2 image). Older single-board releases are never offered to the pull flow. Tags must be `v<semver>` without `+build`; others, missing images and images under 128 KB are skipped with a note on stderr. `size` and `sha256` are those of `smart-grind-by-weight-<tag>.bin` (the raw app image, the same file the WiFi push uploads). `published` comes from the releases API (`published_at`, date part), falling back to the file's mtime (in CI that is the deploy date, since the files were just downloaded); a failing API call is ignored so it can never block the deploy.
- **Channels:** `stable` = highest non-prerelease, `beta` = highest overall (so beta also reports a stable release when it is the newest). Prerelease means a SemVer prerelease part (`-rc.1`), not the tag text.
- **Schema 1 (flat on purpose, same parser style as `http_parse_begin_request`):** `{"schema":1,"channel":"stable","version":"1.5.0","tag":"v1.5.0","prerelease":false,"published":"2026-11-01","size":2240000,"sha256":"<64 hex>","url":"https://devnullgamer.github.io/smart-grind-by-weight/firmware/v1.5.0/smart-grind-by-weight-v1.5.0.bin"}`. No qualifying release: `{"schema":1,"channel":"stable","none":true}` (the UI will say "No release published").
- **SemVer 2.0 rule** (`semver_parse` / `semver_compare` in `src/network/release_index.*`, `semver_parse` / `semver_compare` in the generator): `MAJOR.MINOR.PATCH` plain decimals without leading zeros (max 9 digits), optional `-prerelease` (dotted identifiers `[0-9A-Za-z-]+`, numeric ones without leading zeros), optional `+build` (validated, ignored). A leading `v`, a partial core or trailing junk is rejected; version strings are limited to `UPDATE_VERSION_MAX_LEN` (32). Precedence: core numerically; a release outranks its prereleases; prerelease identifiers compared one by one (numeric by value, numeric below alphanumeric, ASCII order, shorter list lower). `release_is_newer(installed, offered)` is true only when both parse and offered is strictly higher, so an installed rc of the next version never gets an older stable offered and equal versions are "up to date". The same vector lists live in `test_native/test_release_index.cpp` and `tools/tests/test_update_index.py`; change both together.
- **Parser limits** (`release_parse_index`): body <= `UPDATE_PULL_INDEX_MAX_BYTES` (2048), strings <= 128 chars printable ASCII without escapes, no nesting, duplicate keys rejected, unknown flat keys tolerated, `schema` must be 1, `channel` stable/beta, `tag` must equal `v` + `version`, the `prerelease` flag must agree with the version, `published` `YYYY-MM-DD`, `size` within [`UPDATE_IMAGE_MIN_SIZE`, slot size] (slot size is a parameter), `sha256` 64 hex, `url` must start with `UPDATE_PULL_BASE_URL`, end in `.bin` and contain no `..`. The `none` document must carry nothing but schema, channel and `none:true`. The host (base URL) is a firmware constant; the JSON can only add a path below it.
- **Test fixture:** `test_release_index.cpp` embeds the generator's real output (run against a fake `firmware/` tree with single-board, unified, rc and bad-tag releases, and an empty tree for the `none` file). Regenerate the literals if the schema changes. `test_update_index.py` also asserts that the generator's base URL, file names, minimum size and schema equal the constants in `src/config/update.h`.
- **Merging upstream:** `UPDATE_PULL_BASE_URL` (`src/config/update.h`) and `BASE_URL` in `tools/update_index.py` must be changed together (a test compares them).
- **Generator limits:** a release is skipped when its image URL exceeds 128 characters, its version exceeds 32, or its index file would reach 2048 bytes, so a release the device parser would refuse can never become the channel head. The parser also takes the channel it fetched (`expected_channel`): a mismatch, or a prerelease in a stable file, is refused; the URL tail after the base may only contain `[A-Za-z0-9._/-]`.
- **No signing.** The index and image are exactly as trustworthy as the Pages deployment and the TLS chain (the SHA-256 in the index protects against transport corruption, not against a compromised Pages site). Out of scope; to be listed in the security notes.

### HTTPS pull engine (chg008 R6)

**Status:** firmware engine, PC test server and host tests only. Nothing calls the engine from the UI yet (R7), so the main env's linker drops it (`--gc-sections`); the wifi-dev pull envs link it and drive it with `DEBUG_PULL_AUTORUN`. Not yet run on hardware.

- **Files:** `network/pull_logic.*` (pure, host-tested: states, transitions, failure texts, precondition order, index verdict, HTTP response checks, read classification), `network/release_client.*` (`esp_http_client` wrapper), `network/update_pull.*` (job object + worker task), `system/mbedtls_psram_override.*` (TLS allocator), `network/update_pull_autorun.*` (dev only), `tools/wifi/pull_test_server.py`.
- **Flow:** `UpdatePull::request_check(include_prereleases)` / `request_install()` never block and may be called from any task; each moves the state machine (IDLE / CHECKING / UP_TO_DATE / AVAILABLE / CHECK_FAILED / DOWNLOADING / VERIFYING / INSTALLED / FAILED, transition table in `pull_logic.cpp`) with a compare-and-swap and starts the worker task `UpdatePull` (10 KB internal stack, priority 1 below the UI task at 2, core 0; stack high-water is logged when it ends). A refused request leaves the state alone; `refusal()` says why (order: state, WiFi, update/prompt in progress, grinder busy, [install only: unconfirmed image, Bluetooth client], internal heap >= 42 KB). Check: fetch `<base>update-<channel>.json` (<= 2 KB), `release_parse_index` (R5), `pull_evaluate_index` (strictly newer than `BUILD_FIRMWARE_VERSION`, else UP_TO_DATE; an empty channel is UP_TO_DATE with `no_release()`). Install: open the HTTPS connection and validate the reply, then `UpdateGuard::acquire()`, expected-version marker (`ota_marker_store(-1, version)`; the version is compared after the reboot), `ImageSink::begin(size, sha256)`, read 4 KB chunks into a PSRAM buffer and `sink.write`, `client.close()`, `sink.finish()` (SHA-256, `esp_ota_end`, set boot partition), restart after `UPDATE_RESTART_DELAY_MS`. The guard stays held until the restart, like a push update.
- **Deviation from the written order:** the plan listed guard, marker and sink before the TLS open. The worker opens the connection and checks the reply first, so a 404, a redirect, a missing Content-Length or a size that differs from the index ends the job before the grinder is locked, the tasks are suspended or a flash byte is written (the "rejected before any flash write" edge case). The connection idles about a second while the guard and the slot are prepared.
- **Failure paths:** every failure after the guard was granted runs `abort_install()` in the order of `UpdateServer::abort_session_locked()`: sink abort, guard release (tasks run again), marker removal (only if this job obtained the guard, so a refusal never wipes the marker of a running BLE update), `UpdateStatus::set_failed(reason)` (also only when this job owned the guard, so a refused pull never overwrites the status of a push that holds it). The connection is closed by the client object on return, before the guard goes. The boot partition changes only inside `sink.finish()`. Reasons are short display texts from `pull_failure_text()` (No connection, Not found, Server error, Bad server reply, Reply too large, Invalid release info, Download stalled / interrupted, Connection lost, Checksum mismatch, Not a firmware image, Image rejected, Flash write failed, Low memory, ...).
- **Exclusion:** the pull job has its own `UpdateGuard` instance; exclusion with push and BLE is the system-wide `UpdateGuard::is_held()`: a push `begin` answers 409 while the pull holds the guard, and a pull whose `acquire()` fails (push or BLE running) ends as FAILED "Another update running". A Check takes no guard (a push may start during it; push wins). A Bluetooth client or data export that appeared since the request is refused right before the guard; later connections are refused by `onConnect()` while the guard is held.
- **Release client rules:** `https://` only (`http://` only with `DEBUG_PULL_ALLOW_HTTP`), certificates verified against the ESP-IDF bundle (`esp_crt_bundle_attach`), `disable_auto_redirect` (a 3xx is a failed status), status must be 200, `Content-Length` must be present and, for the image, equal to the size in the index (chunked replies are refused), keep-alive off, 15 s socket timeout (`UPDATE_PULL_READ_TIMEOUT_MS`; no data for that long ends the job with "Download stalled"). The host is never taken from the server: URLs are built from `UPDATE_PULL_BASE_URL`, and the parser only accepts index URLs below it.
- **No certificate expiry check:** the device has no system time (no SNTP) and the libs are built without `CONFIG_MBEDTLS_HAVE_TIME_DATE`, so validity dates are not checked; the chain, hostname and signature still are. A revoked or expired certificate is therefore not detected. Accepted for now; the integrity of the image rests on the SHA-256 from the index (same trust as the Pages deployment, no signing).
- **TlsPsramScope (why PSRAM TLS):** the precompiled mbedTLS allocates from internal RAM, and a handshake needs about 40 KB there, which does not fit next to the BLE stack (spike: TLS failed with BLE on and in repeated cycles; with the allocator in PSRAM it worked with BLE on, lowest internal free 36.8 KB, 55 KB/s). `mbedtls_psram_override.cpp` defines `esp_mbedtls_mem_calloc` / `esp_mbedtls_mem_free`, the only two symbols of the archive member `esp_mem.c.obj` in `libmbedcrypto.a`, so the linker never pulls that member (no duplicate symbols; verified in the map file: `esp_mem.c.obj` is absent, one definition each). While a `TlsPsramScope` (RAII, process-wide atomic depth counter, nests) is alive the calloc is `heap_caps_calloc(SPIRAM | 8BIT)` with an internal fallback; outside any scope it is `heap_caps_calloc(INTERNAL | 8BIT)` and free is `heap_caps_free`. **Stock semantics checked:** the ESP-IDF C source is not part of the PlatformIO install (prebuilt libs only), so the stock functions were read from the disassembly of `esp_mem.c.obj` (xtensa objdump): `esp_mbedtls_mem_calloc(n, size)` is one call `heap_caps_calloc(n, size, 0x804)` (`MALLOC_CAP_INTERNAL` 0x800 | `MALLOC_CAP_8BIT` 0x4) and `esp_mbedtls_mem_free(p)` is `heap_caps_free(p)`; sdkconfig has `CONFIG_MBEDTLS_INTERNAL_MEM_ALLOC=y`. The scope wraps the whole job (index fetch or download), memory allocated inside may be freed outside and the other way round. Because the counter is global, any other mbedTLS user active at that time (e.g. the WiFi supplicant) also allocates from PSRAM, which is functionally harmless. Counters of PSRAM allocations and internal fallbacks inside scopes are exposed (`tls_psram_scope_*_allocs()`) and printed by the smoke test.
- **Fallback to the unscoped override:** build with `-DUPDATE_PULL_TLS_PSRAM_UNSCOPED=1` and every allocation becomes PSRAM-first all the time, exactly what the F4 spike measured (the spike env `...-wifi-spike-tlspsram`, `DEBUG_SPIKE_TLS_PSRAM=1`, still implies it and keeps its big-allocation statistics). Use it if the scoped variant misbehaves on hardware.
- **Download deadline:** the whole image download must finish within `UPDATE_PULL_DOWNLOAD_MAX_MS` (10 min, `pull_download_deadline_exceeded`, wrap-safe); past it the job aborts like any failure with "Download stalled", so a server that trickles bytes cannot keep the grinder locked. The marker store result is checked and a failure only logs a warning (the update proceeds, a bad boot would then not be reported).
- **Heap gates (acceptance numbers to verify on COM15, logged as `[HEAP]` lines):** start refused below 42 KB free internal heap (`UPDATE_PULL_MIN_FREE_INTERNAL_BYTES`; measured on COM15: free at job start 47.7-56.5 KB, TLS dips about 9 KB below the start value, lowest seen during TLS 44 KB, so 50 KB refused installs spuriously); internal free never below 30 KB during TLS (spike 36.8 KB); back within 4 KB of the starting value 10 s after the job, 3 repeated runs. Log points: `pull job start`, `connection established` (after the TLS handshake and reply headers), every 256 KB of the download, `pull job end` (all with free, largest block, lowest ever, PSRAM free).
- **Dev knobs (wifi-dev envs only; `update.h` `#error`s without `DEBUG_WIFI_DEV_CREDS`):** `DEBUG_PULL_ALLOW_HTTP` (set in the wifi-dev env), `DEBUG_PULL_BASE_URL` or `SPIKE_PULL_BASE_URL` in the gitignored `include/spike_secrets.h` (replaces `UPDATE_PULL_BASE_URL`, e.g. `"http://192.168.1.20:8080/"`; the secrets override is skipped when `DEBUG_PULL_AUTORUN == 2`, so the smoke env always uses the real Pages URL), `DEBUG_PULL_AUTORUN` (env `...-wifi-dev-pull`: 1 = Check + Install about 25 s after boot, once WiFi is up and the image is confirmed, `[PULL][AUTORUN]` lines, beta channel unless `-DDEBUG_PULL_AUTORUN_BETA=0`; env `...-wifi-dev-pull-smoke`: 2 = three HTTPS runs against the real Pages site, index plus a discarded `.bin` download with the production scope and BLE advertising, `[PULL][SMOKE]` lines and heap gates). None of this exists in the main env.
- **Test server:** `python3 tools/wifi/pull_test_server.py --image .pio/build/<env>/firmware.bin [--port 8080] [--base-url http://<pc>:8080/] [--version X] [--fault F]` serves `update-stable.json` / `update-beta.json` built by `tools/update_index.py` (same documents as the real generator, `url` below the base URL, so it must equal the firmware's base) and the image. The version offered is the one inside the image unless `--version` is given; a prerelease version appears only on the beta channel (stable reports none), so release-candidate test images need the beta channel, which AUTORUN uses by default. If the offered version differs from the one the installed image reports, the device shows the update-failed screen after the reboot (the marker compares versions), expected in tests that fake the version. The server listens on this PC's LAN address by default (never 0.0.0.0 unless `--host 0.0.0.0` is given, with a warning). Faults and the reason the device shows (measured on COM15): `wrong-sha` (Checksum mismatch), `truncate` (Connection lost), `kill` (reset, then the server exits; Download stalled), `stall` (Download stalled), `404` (Not found), `oversize` (Content-Length 4 KB larger than the index; Reply too large), `older` (offers 0.0.1), `not-image`, `no-release`. pytest: `tools/tests/test_pull_test_server.py`.
- **Not covered by tests yet:** everything that needs the device (TLS, heap gates, the push/pull exclusion in both directions, the BLE-connected refusal, restart into the new build); the real `update-stable.json` on Pages does not exist before the first release after the next deploy.

### Pull UI in the WiFi page (chg008 R7)

Menu -> WiFi -> "Firmware" section (below Updates). Nothing here touches LVGL from the worker: the UI task reads `update_pull` (state, offer, failure, `result_at_ms()`) at 1 Hz and on every tap; all texts and decisions are pure (`network/pull_ui_text.*`, `network/update_ui_logic.*`, host tests).

- **Layout (280 px):** `Installed:` (stacked row, `v1.4.1-rc.3 (#217)`), `Latest:` (stacked: `--`, `Checking...`, `v1.5.0` in the success colour, `Up to date`, `No release published`, `Check failed`, `Install failed`, `Check again` when stale), description + `Beta` toggle (NVS `beta`, `WiFiManager::beta_channel()`), `Check for update` button (accent; label `Checking...` and disabled while the worker runs; disabled without WiFi), `Install v1.5.0` button (success colour, hidden unless a fresh AVAILABLE result exists; the label wraps to two lines inside the 220 px button for long prerelease versions), and one warning-coloured notice line (check errors, refusals, "Connect to WiFi to check for updates.").
- **State rules:** Install is shown only in AVAILABLE with a known version, WiFi connected and a result younger than 10 min (`UPDATE_PULL_RESULT_STALE_MS`, measured from `UpdatePull::result_at_ms()` set when the job ends, so leaving the page does not extend it). Changing Beta clears the previous result (`update_pull.reset()`) and is ignored (toggle reverted) while a job runs. The result lives in `update_pull`, so re-entering the page shows it again. A refusal message ("Disconnect Bluetooth first.") is held by the page for `UPDATE_PULL_NOTICE_MS` (6 s), also across the Install dialog.
- **Install flow (UI task):** tap Install -> re-check freshness and `UpdatePull::install_refusal()` (new, side-effect free; the pure `pull_refusal` order incl. BLE client connected) -> confirm dialog (version, installed version, size, "Bluetooth is turned off meanwhile") -> INSTALL callback: re-check that the offer is the one shown, `install_refusal()` again, only then `bluetooth_manager->disable()` (UI-task call, same as the Bluetooth toggle) and `request_install()`. So a refused install never switches Bluetooth off; once it is off it stays off after a failure and the notice says so ("turn it on in the Bluetooth page"). Double tap: the first tap switches the UI to CONFIRM (the page is hidden), the Install handler also requires UI state MENU, and the dialog callback is single-shot.
- **Progress:** `WifiUpdateUIController` gets the pull job as a second source. Title `Downloading` (push keeps `WiFi update`), status `Connecting...` from the request until the first flash byte (TLS and validation happen before `UpdateStatus` has anything; `update_pull_progress_view`), then `Downloading update...` with the arc, `Verifying...`, `Installed. Restarting...`. A failure that never reached `UpdateStatus` (404, no connection, refused guard) is shown from `update_pull.failure()`; after the 3 s hold the UI returns to MENU and acknowledges the pull FAILED state once (`pull_failure_acked_`), the state itself stays so the page explains it. The reason on the screen is cut to `UPDATE_UI_REASON_MAX` (16) characters like every WiFi failure ("Failed: Checksum mism..."); the page notice carries the full text. `OtaDataExportController` treats the screen as owned while `WifiUpdateUIController::progress_shown()` (otherwise its 3 s idle rule would throw the connecting phase out). `hold_awake` already covers the whole time the screen is shown. A pull-only view never takes over a screen other than READY / MENU.
- **Not covered by automated tests:** the LVGL widgets and the dialog; user-in-the-loop checklist (Check with the PC test server up, Install with live progress, failure by stopping the server, Beta switching the channel file, BLE-connected refusal with a phone).

### WiFi / update security notes (chg008)

Hardware status of the whole WiFi feature set: push update and Accept handshake ran on a V2 board (COM15) with the wifi-dev env; the pull engine ran against a PC test server there. **Not hardware-verified:** BLE provisioning (`wifi-set`, web flasher tab), every LVGL screen as a user sees it, the real GitHub Pages `update-*.json` (does not exist before the first release after the deploy), and the BLE-connected refusals. Host tests cover the pure logic only.

- **Threat model:** a LAN client (push) and the Pages/GitHub trust chain (pull). There is no firmware signing and no secure boot; the SHA-256 protects against corruption, not against a compromised server or token.
- **Push needs three things:** the Receive toggle armed (default off, persistent), the 16-hex bearer token, and a tap on INSTALL (Confirm default on). Plain HTTP on the LAN: the token travels in clear. Three bad tokens lock authentication for 60 s (doubling to 15 min, global, so a LAN client can lock the user out).
- **Confirm off** removes the physical control: anyone with the token can install firmware unattended. The switch is greyed out without credentials and Confirm is hidden while Receive is off, turning it off needs a warning dialog, and Forget resets it to on.
- **Token handling:** generated on the PC/browser, never returned by the device, never shown on it, never logged. Stored in plaintext NVS together with SSID and password (no NVS encryption); a flash dump reveals them. Regenerate by provisioning again (`wifi-set` / web tab while Menu -> WiFi is open).
- **BLE provisioning link is unencrypted:** a sniffer in radio range can read SSID, password and token while no credentials exist or while the WiFi page is on screen. The debug write path is unauthenticated; the page-open requirement (window) is the only gate.
- **Pull:** HTTPS to the fixed base URL only, certificates checked against the ESP-IDF bundle, no redirects, no certificate expiry check (no system time), integrity by the index SHA-256, trust equals the Pages deployment. Beta channel images are whatever the newest release is.
- **Rollback is the safety net, not a security control:** it protects against an image that crashes in the first 30 s, nothing else. The first update from a pre-R4 firmware is not protected.
- **Dev builds:** the wifi-dev envs seed a public dev token and arm push; erase NVS afterwards (see WiFi manager section). `DEBUG_*` pull and autoreply knobs `#error` without `DEBUG_WIFI_DEV_CREDS` and never reach the main env.
- **Client text on the grinder screen** (version, address) is sanitised to printable ASCII; HTTP replies never contain secrets.

### Known loose ends

- Hardware validation matrix on both boards (cold-boot visuals, forced UNKNOWN, OTA migration from old V1/V2 images) is tracked outside the repo.
- `LICENSE` still lists Arduino_GFX although the library is no longer used.

## Safety batch 1 (chg003 items 1-5, chg004 items 7 and 11)

Goal: a faulty sensor, a stuck phase, a lost motor command or an interrupted update must never leave the motor running or the grinder stuck. Decisions D1-D13 were approved on 2026-10-21 and are implemented as listed below.

### Layout
- Pure, host-testable modules (no Arduino/ESP includes, in `platformio-native.ini`, tested in `test_native`): `src/hardware/sensor_health.*` (sample age, stale check, settled check), `src/controllers/grind_safety.*` (phase timeouts, no-flow decisions, pulse wait limit), `src/hardware/rmt_pulse_math.*` (deadman time, exact RMT pulse symbols).
- `GrindController` supplies measurements and acts on the answers. `check_safety()` runs once per control cycle after the pause early-return and before the phase switch; its aborts go through `raise_safety()`, which applies the kill switch and calls `abort_grind()` (`Err: motor` calls `abort_grind()` directly and ignores the kill switch). `abort_grind()` stops the motor, sets `last_session_result_ = ERROR`, queues a `[SAFETY]` log line, sets the UI text and switches to `TIMEOUT` (the session log still says TIMEOUT). A future command queue slots in before the `check_safety()` call.
- Constants live in `src/config/grind_control.h` and `src/config/hardware.h`; include them through `constants.h`.

### Thresholds
| What | Value | Constant |
|---|---|---|
| Newest sample older than this = sensor stale, abort `Err: sensor` | 500 ms (5 missed samples at 10 SPS) | `HW_LOADCELL_STALE_SAMPLE_MS` |
| Stale this long (after the first sample ever) raises `HX711_NO_DATA` | 2000 ms | `HW_LOADCELL_NO_DATA_DIAG_MS` |
| Settled check needs this many samples in its window | max(2, 60% of the samples expected at 10 SPS) | `HW_LOADCELL_SETTLE_MIN_SAMPLES_PERCENT`, `..._FLOOR` |
| TARE_CONFIRM: tare still running -> abort `Err: tare` | 5 s | `GRIND_TARE_CONFIRM_TARE_TIMEOUT_MS` |
| TARE_CONFIRM: not settled after the tare finished -> continue anyway | 10 s | `GRIND_TARE_CONFIRM_SETTLE_TIMEOUT_MS` |
| FINAL_SETTLING / PULSE_SETTLING / PULSE_DECISION fallback | 4 s | `GRIND_SETTLE_FALLBACK_MS` |
| PRIME: cup holds < 50% of the purge amount at 5 s -> abort `Err: no flow` | 50%, 5 s (the prime run limit) | `GRIND_PRIME_NO_FLOW_MIN_PERCENT`, `GRIND_PRIME_NO_FLOW_CHECK_MS` |
| PREDICTIVE: peak gain over the lowest reading < 0.3 g at 4 s -> abort `Err: no flow` | 0.3 g, 4 s | `GRIND_PREDICTIVE_NO_FLOW_MIN_GAIN_G`, `..._CHECK_MS` |
| PULSE_EXECUTE / TIME_ADDITIONAL_PULSE wait for `is_pulse_complete()` | pulse length + 1 s, then the motor is stopped and the phase moves on | `GRIND_PULSE_WAIT_MARGIN_MS` |
| Longest finite pulse `start_pulse_rmt()` accepts | 4000 ms | `HW_GRINDER_MAX_PULSE_MS` |
| Continuous-run motor deadman | `GRIND_TIMEOUT_SEC` + 2 s = 62 s | `HW_GRINDER_DEADMAN_MARGIN_MS` |

### Decisions as implemented
- **D1 weight mode only.** `check_safety()` returns immediately in time mode. It runs only in TARE_CONFIRM, PRIME, PRIME_SETTLING, PREDICTIVE, PULSE_DECISION, PULSE_EXECUTE, PULSE_SETTLING and FINAL_SETTLING, never while paused (PURGE_CONFIRM).
- **D2 stale 500 ms.** The stale check is first in `check_safety()`. A buffer with no sample at all is stale. The largest sample age seen is tracked per grind (`max_sample_age_ms_`) and printed as `[SAFETY] Max load cell sample age`. All `[SAFETY]` lines go through `queue_log_message` -> `LOG_BLE`, which is `Serial.printf`: they are best-effort serial-monitor lines, not part of the session CSV/log, and are dropped if the queue is full.
- **D3 TARE_CONFIRM.** Tare not finished after 5 s aborts with `Err: tare`. Once the tare is done, a scale that does not settle for 10 s continues anyway (found by code review as the cause of the "noisy cell -> timeout screen" symptom).
- **D4 PULSE_DECISION timeout -> finish.** No settled reading after 4 s moves to FINAL_SETTLING with the current reading.
- **D5 fallback 4 s.** PULSE_SETTLING falls through to PULSE_DECISION after 4 s; FINAL_SETTLING uses the current reading.
- **D6 mid-grind stall abort deferred.** Only PRIME and PREDICTIVE have no-flow aborts; a flow that stops later in the grind is not detected.
- **D7 no-flow numbers** as in the table. The predictive baseline is the lowest weight seen since phase entry, so a tap on the cup cannot inflate it. Elapsed time is clamped at 0 so an ordering race cannot underflow into a false abort.
- **D8 OTA refused during a grind**, autotune or any motor activity (see OTA fail-safe).
- **D9 MOTOR_FAULT latched until reboot** (typically a run over 62 s; also raised if `halt_output()` fails to stop the RMT output, and only then is the motor really dead; otherwise the latch is a warning) (`deadman_tripped_since_boot()`, set on the UI task in `check_board()`). It outranks MOTOR_DISABLED in warning priority. Text: "Motor output was cut off. Check the grinder and restart the device."
- **D10 saved latency kept.** The user must re-run autotune once after this firmware (see exact RMT pulses).
- **D11 kill switch.** `GRIND_SAFETY_ABORTS_ENABLED` (default 1). With 0, `raise_safety()` only queues a `[SAFETY] ... (aborts disabled, log only)` line (once per reason per grind) and the grind continues. It covers `Err: sensor`, `Err: tare` and `Err: no flow`. It does not cover the motor deadman or the pulse wait stop.
- **D12 self-test run with the grinder disconnected from mains.** An oscilloscope is optional (pin-low timing agreed with the callback within ~1 ms).
- **D13 boot NO_DATA mapped to `HX711_NO_DATA`.** The boot fault `HardwareFault::NO_DATA` used to map to no warning at all. `HX711_NO_DATA` is also raised at runtime when a sensor that has delivered samples has been silent for 2 s (never before the first sample, so bring-up does not warn). It is derived on the UI task in `check_load_cell_boot_fault()` (diagnostics are not thread safe) and clears when samples return.

### Abort texts (UI text, session result ERROR)
- `Err: sensor`: log `LOAD CELL STALE` with the newest sample age or "no sample".
- `Err: tare`: log `TARE NOT COMPLETING`. The tare needs 18 samples (`DATA_SET` in `WeightSensor.h`), independent of cup or settling, so this means samples arrived too slowly (under ~3.6 SPS over 5 s; a fully stale sensor gives `Err: sensor` first). Cause inferred from code only.
- `Err: no flow`: log `NO FLOW IN PRIME` or `NO FLOW IN PREDICTIVE` with the measured weight/gain.
- `Err: motor`: log `MOTOR DEADMAN TRIPPED`, raised from `GrindController::update()` when `grinder->consume_deadman_trip()` fires. The flag is consumed before the idle check so a trip outside a grind (Motor Test) is not carried into the next one.

### Motor deadman and lock-out (`src/hardware/grinder.cpp`)
- `Grinder` has a mutex and atomics. A continuous run arms an `esp_timer` deadman (62 s) before the motor can start; if the timer cannot be created or armed, the start is refused. The normal 60 s timeout always wins; the deadman is the last resort.
- The deadman is cancelled only after `halt_output()` has verified the RMT output is stopped; if stopping fails the pins are forced low (`force_motor_pins_low()`). A pulse requested over a running continuous run first halts that run, so it cannot defeat the deadman.
- The deadman callback runs in the esp_timer task, logs with `esp_rom_printf` only, and proceeds without the mutex after 20 ms: stopping the motor outranks consistency.
- `lock_out()` stops the motor and makes start and pulse requests fail until `unlock()`. It is used by the OTA path.
- `DEBUG_GRINDER_DEADMAN_TEST` makes the deadman fire 3 s after motor start (env `...-deadman-test`). Expected result for any longer continuous run: `Err: motor` and the MOTOR_FAULT warning. `DEBUG_GRINDER_DEADMAN_AUTORUN` (only with the `...-deadman-test` env, `#error` without `DEBUG_GRINDER_DEADMAN_TEST`; `src/hardware/grinder_deadman_test.*`) starts one continuous run about 6 s after boot, so the motor really runs 3 s on every boot with a grinder connected (disconnect mains). Serial lines: `[DEADMAN-TEST] WARNING ...` at boot, `starting continuous run`, `mid-run: pin 16 HIGH`, `[Grinder] DEADMAN: continuous run exceeded 3000 ms`, `result: deadman tripped, fault latched, pin LOW`. Other results: `skipped: ...` (not initialized, or busy / locked out / already tripped), `result: FAILED: ...` (start refused, or a check failed) and `result: INCONCLUSIVE: pin read did not see HIGH while running`; failed or inconclusive runs issue `stop()` and log `cleanup`. Hardware: the full expected sequence was seen on a bench V2 with nothing attached (build 304).

### OTA fail-safe (`ota_handler.cpp`)
- `start_ota()` refuses with "Update refused: grinder busy" while a grind, autotune or the motor is active, before any side effect; then it calls `lock_out()` and re-checks (a grind may start in between).
- WiFi push/pull updates go through `UpdateGuard` (`src/system/update_guard.h`), which repeats the same refuse-if-busy, `lock_out()` and `unlock()` sequence and also excludes parallel updates.
- Failed or aborted updates go through one cleanup routine, `cleanup_failed_ota()`: resume hardware tasks first, then restore the normal watchdog timeout (the extended 1800 s value used to stay), re-enable touch, remove the `new_build_nr` / `new_fw_ver` NVS keys and unlock the grinder. The NVS keys are now written only after `start_update()` succeeded.
- `HX711_NO_DATA` can appear during an update because hardware tasks, and with them sampling, are suspended; it clears after the tasks resume.

### Exact RMT pulses (`rmt_pulse_math.*`)
- Finding (self-test on a V1 bench board): the old code used `loop_count` over a short payload. Looping repeats the payload remainder and the 1 us LOW tail on every pass, so pulses over 65.5 ms came out wrong. Measured: 70 -> 37.3, 100 -> 69.0, 550 -> 877.5, 1000 -> 1443.0 ms; 65 ms and below were exact. This is why `loop_count` was dropped.
- Now a pulse is ONE plain payload with no `loop_count`: the HIGH time is split into halves of at most `RMT_MAX_HALF_US` = 32767 us (the 15-bit RMT duration field), packed two per symbol (`RmtSymbol`), followed by a `RMT_PULSE_TAIL_US` = 1 us LOW tail. The unused second half of the final tail symbol has duration 0 (end marker). Capacity is `RMT_PULSE_SYMBOL_CAPACITY` = 64 symbols; 4000 ms needs 62. The payload is transmitted from a member buffer (`pulse_symbols_`); a 64-symbol staging array on the stack is copied into it.
- Measured on a V2 bench board (env `...-rmt-selftest-v2`, build 295): 20..4000 ms all within 0.4 percent (+40-50 us fixed overhead), callback fires once per pulse, no gaps.
- Consequences: the time-mode 100 ms pulse is now a true 100 ms (was ~69 ms); the autotune and Motor Test 1000 ms pulse is 1000 ms (was ~1443 ms). Saved latency was measured with the old, mis-timed pulses (weight-mode correction pulses over ~65 ms were affected too), so autotune must be re-run once.
- `start_pulse_rmt()` refuses 0 ms and more than 4000 ms; `rmt_transmit` errors stop the motor, and a start that is locked out halts a live pulse.

### Debug-only flags
- `DEBUG_RMT_PULSE_SELFTEST` (env `...-rmt-selftest`): at boot, sends pulses over a range of durations and prints requested vs measured (callback and pin-low). DISCONNECT THE GRINDER FROM MAINS.
- `DEBUG_RMT_SELFTEST_FORCE_BOARD_V2` (env `...-rmt-selftest-v2`): establishes the board as V2 (source USER, nothing stored) so a V2 that boots from the cached board can run the self-test. GPIO16 only, never GPIO18. `#error` without `DEBUG_RMT_PULSE_SELFTEST`.
- `DEBUG_GRINDER_DEADMAN_TEST` (env `...-deadman-test`): see above.
- None of these belong in the main env or releases. After a self-test env, reflash the normal build; the self-test image must not grind.

### Start refusal (`grind_start_check.*`)
- `GrindController::start_block()` decides, in this order: motor unavailable (`MOTOR_DISABLED`), grinder locked out (`UPDATE_IN_PROGRESS`), load cell boot fault (`LOAD_CELL_NOT_CONNECTED` / `LOAD_CELL_NO_DATA` / `LOAD_CELL_RATE_INVALID`). The pure function and texts live in `grind_start_check.*` (host-tested); the controller only gathers the inputs, which are atomics or set at init, so polling it from the UI task is safe.
- `start_grind()` returns the block and logs `[GRIND_START] Refused - <reason>`; it is not behind `GRIND_SAFETY_ABORTS_ENABLED`. `handle_grind_button` shows `UIManager::show_start_blocked_notice` (the motor dialog for MOTOR_DISABLED, otherwise "CAN'T START" with OK/BACK). `update_auto_actions` uses `start_block() == NONE` instead of `motor_available()`, so auto-start never triggers a refusal dialog.
- Weight and time mode are treated alike. Not refused: not calibrated, or a sensor that goes quiet only after boot (caught as `Err: sensor` once the grind runs). The notice screen is NOT hardware-verified.

### Known limitations
- **Flatline and saturation are not detected.** The planned checks (10 identical readings, ADC within 4096 counts of the rails) were deferred. A disconnected HX711 (pulled down) that keeps delivering a constant 0x800000 is therefore NOT caught by the stale check: the samples are fresh, they just never change. In weight mode it should surface as `Err: no flow` in PRIME or PREDICTIVE, not as a sensor error (not verified on hardware).
- The stale check assumes ~10 SPS sampling; another rate needs `HW_LOADCELL_STALE_SAMPLE_MS` revisited.
- After `Err: tare` the `doTare` request is not cancelled; the tare may still complete later.
- Time mode has no TARE_CONFIRM / FINAL_SETTLING fallback and no sensor checks (D1).
- `grind_phase_timed_out` with a limit of 0 counts as timed out immediately.
- No-flow thresholds (50% at 5 s, 0.3 g at 4 s) are not field-tuned; the kill switch is the mitigation.
- Weight-mode correction pulses over ~65 ms were also mis-timed by the old looped code and are now exact. Saved latency and correction accuracy were affected, hence the autotune re-run.
- Hardware verification: Build B items (deadman trip, `lock_out`, OTA refuse / abort / stall cleanup, MOTOR_FAULT warning) are NOT RUN - Build B was never flashed and tested. Weight-mode checks, the deadman, lock-out/OTA fail-safe and MOTOR_FAULT have not been run on hardware. Exact pulses were measured on a V2 bench board only (the V1 run measured the old looped code). Build C items (stale abort with the cable pulled, tare abort, settle fallbacks, prime/predictive no-flow, `HX711_NO_DATA` at runtime) are NOT RUN - need a sensor. Only the RMT self-test ran on bench boards without a load cell (V1: old code, V2: exact code). Host tests cover the pure logic only; `check_safety()` and the `is_settled` wiring need Arduino and are not host-testable.
